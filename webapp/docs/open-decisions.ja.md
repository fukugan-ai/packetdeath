# 残る判断と、それぞれを止めている物

本番の WebApp は、最初の管理者の登録と第二要素（TOTP）の有効化まで済んでいる。次の 5 件は、止めている物が外れた手番で入れる。

| 項目 | 推奨 | 止めている物 | 入れ方と戻し方 |
|---|---|---|---|
| passkey を本番で使う | 画面を開く URL を 1 つに固定し、`--rp-id` と `--origin` をその URL に一字違わず合わせる。ブラウザが信用する HTTPS の名前があれば、別の PC からも使える | 画面を開く URL が決まっていない（localhost への SSH トンネルのポート、または HTTPS の名前） | webapp の unit の drop-in に 2 つの引数を足して 1 回再起動する。戻しは drop-in を消す。TOTP と回復 code はそのまま動く |
| 保存時の暗号化（PD-BL1） | 方式 A（WSL 内の LUKS）。ホスト側の暗号化（B）は WSL の vhdx を守るが、WSL 内のプロセスからは平文に見える | データの移し替えが戻せない操作で、移す前の控えと停止時間の確認が要る | 新しい暗号化 volume を作り、複写して照合してから差し替える。戻しは元の volume に戻すこと |
| WAF の `--mode block` | 実際の保護対象を前に置いた時点で、`detect` で 1 週間の `waf-report` を見てから切り替える。いまの WAF は無害な上流の canary で、遮断する相手がない | 保護する実サービスが未定 | unit の `--mode` を `block` に替えて 1 回再起動する。戻しは `detect` に戻すこと |
| Windows PW-4 と再起動試験 | 利用者の PC で行う | 実機の操作が要る（PC の再起動と、起動後の確認） | `blocklists/README` の手順書の通り |
| Chrome の保存と自動入力 | 実機で次のサインインのときに確かめる | ヘッドレスのブラウザでは Chrome の保存の確認画面が出ない | 出なければ、画面の `PasswordCredential` の呼び出しを見直す |

## 採らない手段

- passkey を `--rp-id` と `--origin` なしで有効にする：画面を開く URL と一字でも違うと、ブラウザが登録も署名も拒否するため採らない。
- パスワード管理の保存を Chrome の提案だけに任せる：提案は 15 文字で、最低 128 文字の欄に入らないため採らない。画面が 128 文字を作るボタンを持つ。
- 暗号化を pgcrypto など列ごとの暗号にする：検索と索引が効かなくなり、鍵の置き場が結局 host の中になるため採らない。
- WAF を保護対象の無いまま `block` にする：遮断する相手がなく、誤検知の確認もできないため採らない。
